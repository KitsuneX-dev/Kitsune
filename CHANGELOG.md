# Changelog

All notable changes to Kitsune Userbot are documented here.

---

## [1.4.4-hotfix.2] — Команды после обновления с 1.4.3

- Исправлен оставшийся взаимный блокирующий сценарий запуска: живой цикл
  Telethon теперь планируется **до** `catch_up()`. Догон пропущенных обновлений
  выполняется отдельной фоновой задачей и больше не может навсегда оставить
  загруженные `.help`, `.ping` и остальные команды без Telegram-событий.
- Неожиданная остановка update loop больше не маскируется работающей веб-панелью:
  исходная ошибка Telethon передаётся наверх и попадает в журнал.
- Overlay-миграция 1.4.3 → 1.4.4 теперь удаляет полный набор из восьми старых
  исходников, включая забытый `kitsune/secure/__init__.py`, а также безопасно
  убирает старый `secure/__pycache__`. Локальные расширения в `secure`, конфиг,
  сессии, БД и пользовательские модули сохраняются.
- Добавлены регрессионные тесты зависшего `catch_up()`, видимости ошибки update
  loop и полной очистки overlay-установки.

## [1.4.4-hotfix] — Первая попытка исправления обновления

- Цикл Telethon был перенесён в параллельную startup-задачу, однако внутри неё
  всё ещё ожидался `catch_up()` до запуска `run_until_disconnected()`. На
  проблемной сессии это сохраняло исходное «молчание» команд.
- Добавлена первая версия allow-list очистки семи устаревших файлов 1.4.3.

## [1.4.4] — Безопасность, целостность данных, инфраструктура и плейсхолдеры

Крупнейший сводный релиз проекта. Сюда вошли: закрытие веб-панели и мастера
первичной настройки аутентификацией, устранение молчаливой потери данных из-за
пропущенных `await`, переход бэкапов на PBKDF2, полная верификация SSL,
корректный перезапуск процесса, переезд Docker на multi-stage с рабочим томом
данных, реальные CI-проверки, разбор монолитов на пакеты — а также ранее
анонсированные алиасы команд, replay-защита MTProto, единый `utils`,
плейсхолдеры `.info`/`.ping`, честные метрики веб-панели, закрытие трёх пробелов AST-сканера и единый режим прав каталогов с данными.

### 🔐 Безопасность — AST-сканер (`kitsune/core/loader.py`)

- **`getattr` со свёрнутым именем атрибута.** `getattr((), '__cla' + 'ss__')`
  проходил проверку: внутри одного файла `attrgetter` и `sys.modules` уже
  сверялись через `_ASTScanner._folded_str`, а `getattr` — только через
  `ast.Constant`, то есть конкатенация литералов и f-строка без подстановок
  сканер обходили. Проверка переведена на `_folded_str`, поэтому все три
  канала теперь согласованы. Ветка «вычисляемое имя атрибута на модуле» при
  этом сохранена и больше не задевает нестроковые константы.
- **Ключ `vars()` / `globals()` / `locals()`.** `vars(obj)['__subclasses__']` —
  тот же побег, что `obj.__subclasses__`, только через `__dict__`; ключ
  сверялся лишь со списками модулей и os-атрибутов. Теперь он проверяется и
  против `_SANDBOX_ESCAPE_ATTRS` (плюс `_ASYNC_SUBPROCESS_ATTRS`), а сам ключ
  сворачивается тем же `_folded_str`.
- **Строки формата.** `'{0.__class__.__base__.__subclasses__}'.format(())`,
  `'{0.__class__}'.format_map(...)`, `Formatter().vformat(...)` и
  `Formatter().get_field('0.__class__', ...)` не оставляли в AST ни
  `ast.Attribute`, ни вызова `getattr` — по атрибутам ходит сам движок
  форматирования в рантайме. Добавлен статический разбор шаблона
  (`_format_template_sensitive_attr` / `_field_path_sensitive_attr`): поля,
  индексация `{0[__class__]}` и вложенные спецификаторы `{0:{1.__class__}}`
  сверяются с `_SENSITIVE_ATTR_NAMES`. Битый шаблон сканер не роняет, обычное
  форматирование (`'{}'`, `'{name}'`, `'{0.id}'`, `'{:>10}'`, `'{0.__name__}'`)
  остаётся разрешённым.

### 🔧 Права каталогов — единая точка истины (`kitsune/paths.py`)

- Режим каталога с данными ставился в трёх местах с разными значениями:
  `main.py` — `0o755`, `session_enc.py` — `0o700`, `accounts_manager.py` —
  `0o755` на каталог аккаунта, где лежат сессии. Итог зависел от того, кто
  отработал последним.
- В `paths.py` добавлены константы `PRIVATE_DIR_MODE` (0700) и
  `PRIVATE_FILE_MODE` (0600) и хелперы `harden_dir()` / `harden_file()`.
  На них переведены `main.py`, `session_enc.py`, `accounts_manager.py`,
  `crypto.py`, `account_setup.py` и `__init__.py`; литералов `0o755` вне
  встроенных модулей больше нет. Каталог аккаунта, `modules/` и `logs/` теперь
  тоже `0700`, а не `0755`. На платформах без POSIX-прав `chmod` по-прежнему
  не роняет запуск — пишется debug-сообщение.

### ⚡ Производительность сети и загрузки модулей

- **Единый `aiohttp.ClientSession` вместо сессии на каждый запрос.** Было: семь
  мест (`modules/weather.py`, `modules/translations.py`, `modules/loader_mod.py`
  — три вызова, `translations.py`, `core/loader.py`) открывали
  `async with aiohttp.ClientSession() as ...`, то есть на каждый HTTP-запрос
  выполнялся новый TCP+TLS хендшейк, а пул соединений умирал вместе с блоком.
  Стало: новый модуль `kitsune/net/http_pool.py` лениво создаёт одну общую
  сессию с переиспользуемым `TCPConnector` (`limit=100`, `limit_per_host=10`,
  `keepalive_timeout=30`, `enable_cleanup_closed=True`); потребители берут её
  через `get_shared_session()` (экспортируется из `kitsune.net`) и не закрывают
  сами. Закрытие — один раз в `core/lifecycle.shutdown()` через
  `close_shared_session()`. Почему: повторные обращения к репозиториям модулей,
  языковым пакетам и wttr.in переиспользуют keep-alive соединение, вместо
  того чтобы каждый раз платить за рукопожатие. Вызовы в `net/proxy_sources.py`,
  `net/ssl_ctx.py`, `modules/notifier/*` и `modules/rkn_bypass.py` намеренно
  оставлены со своими сессиями: у них особые коннекторы (SOCKS/без верификации).
- **AST-скан модулей больше не повторяется после перезапуска.** Было:
  in-memory `_ast_cache` (`OrderedDict[str, ast.AST]`, LRU на 128 записей)
  жил только внутри процесса — после рестарта каждый модуль парсился и
  сканировался заново. Стало: в `core/loader.py` добавлено множество
  `_ast_scan_ok_hashes: set[str]`, которое сохраняется в
  `DATA_DIR/.ast_scan_ok.json` (только sha256-хэши, без деревьев — они не
  сериализуются). `_load_ast_scan_cache()` подтягивает файл один раз лениво,
  запись идёт батчем (каждые 25 новых хэшей) и один раз на shutdown через
  `flush_ast_scan_cache()`; предел файла — 50 000 хэшей, права `0700` на
  каталог и `0600` на файл через уже существующие `harden_dir`/`harden_file`.
  Почему: старт с десятками пользовательских модулей больше не тратит время на
  повторный парсинг заведомо проверенного кода. Безопасность не страдает —
  ключ это sha256 содержимого, при любой правке файла хэш меняется и скан
  выполняется заново.

### 🔐 Безопасность

- **Веб-панель закрыта аутентификацией.** При первом запуске генерируется
  криптостойкий токен (`secrets.token_urlsafe(32)`), он сохраняется в БД
  (`kitsune.web` → `access_token`), пишется в лог и отправляется владельцу в
  «Избранное» вместе с готовой ссылкой для входа. Новый модуль
  `kitsune/web/auth.py` даёт aiohttp-middleware, которая требует токен на ВСЕХ
  роутах кроме `/health`. Токен принимается из заголовка
  `Authorization: Bearer <token>` либо из httpOnly + `SameSite=Strict` cookie,
  выставляемой при заходе по `/?token=...`. Сравнение — строго
  `hmac.compare_digest` (защита от timing-атак). Добавлен rate-limit на
  неудачные попытки (10/мин на IP) с временной блокировкой на 5 минут.
  В `web/dashboard_html.py` все 13 вызовов `fetch()` переведены на общую
  обёртку, подставляющую заголовок с токеном.
- **Мастер первичной настройки больше не отдаёт аккаунт кому попало.** Раньше
  `kitsune/web/setup.py` слушал `0.0.0.0:8080` вообще без аутентификации и
  принимал через `/api/sendcode` → `/api/signin` → `/api/2fa` код входа в
  Telegram и пароль двухфакторной аутентификации — любой в локальной сети мог
  угнать аккаунт. Теперь мастер по умолчанию биндится на `127.0.0.1`, наружу
  открывается только при явно заданном `web_host`, и в этом случае обязателен
  одноразовый setup-токен, печатаемый в консоль и вшитый в показываемую
  ссылку. При биндe на `0.0.0.0` в лог пишется явное предупреждение.
- **Убрана CORS-вседозволенность.** `Access-Control-Allow-Origin: *` из
  `web/core.py` удалён. CORS теперь работает только по явному allowlist из
  конфига (по умолчанию пуст), заголовки выдаются через
  `_build_cors_middleware()`. На ответы добавлены security-заголовки:
  `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: no-referrer` и минимальный `Content-Security-Policy`.
- **Дефолтный биндинг веб-панели — `127.0.0.1`.** В `core/lifecycle.py`
  значение `web_host` по умолчанию изменено с `0.0.0.0`; как осознанно открыть
  панель наружу, описано в README.
- **Ключ шифрования бэкапов выводится через PBKDF2.** `kitsune/crypto.py`:
  одиночный `sha256` заменён на PBKDF2-HMAC-SHA256 с **600 000 итераций** и
  стабильной солью, привязанной к установке (соль хранится рядом с ключом,
  права `0600`). Обеспечена миграция: сначала пробуется новый ключ, при
  неудаче — ключ прежнего формата, выведенный одиночным `sha256`; в заголовок
  пишется маркер версии формата (`AESGCM2:` / `CHACHA2:`, старые `AESGCM1:` /
  `CHACHA1:` читаются как прежде).
  Старые бэкапы продолжают открываться.
- **SSL-верификация включена по умолчанию.** `make_ssl_ctx_no_verify()`
  использовалась в 8 местах, включая проверку **токена бота** через
  `api.telegram.org` и обращения к GitHub в апдейтере. Функция переименована в
  `make_ssl_ctx(verify: bool = True)` с полной верификацией через
  `ssl.create_default_context()` + `certifi`; старое имя оставлено
  deprecated-обёрткой с `DeprecationWarning`. Отключение верификации допустимо
  только для парсинга публичных списков MTProto-прокси — через явный
  `verify=False` и с предупреждением в лог. `get_aiohttp_connector_with_proxy()`
  по умолчанию верифицирующий.
- **Криптостойкий ГСЧ в FakeTLS.** `kitsune/mtproto_faketls.py`:
  `random.randrange` (Mersenne Twister) для ключа и IV AES-CTR заменён на
  `os.urandom` / `secrets`. `_myrandom.getrandbytes()` и
  `_gen_x25519_public_key()` работают как раньше, рукопожатие FakeTLS не
  сломано.
- **Права доступа к файлам сессии ужесточены.** `0o644` → `0o600` для
  `.session`, `-wal`, `-shm`, `-journal` в `session_enc.py`, `__init__.py` и
  `web/setup.py`; каталог данных — `0o700`. Предусмотрен аккуратный fallback с
  логом, если файловая система не поддерживает `chmod` (FAT/exFAT).
- **Модули из бэкапа проверяются ДО записи в `modules/`.** Раньше `.py` писался
  на диск до AST-сканирования: файл, отклонённый сканером, оставался на диске и
  загружался при следующем старте. Теперь архив распаковывается во временный
  каталог, проходит `loader._scan_ast_with_cache`, и только при успехе файл
  переезжает в `modules/`. Отклонённые файлы уходят в карантин
  (`<data_dir>/quarantine`), пользователь получает отчёт с причиной по каждому.
- **AST-сканер модулей перестал обходиться переименованием.** `_ASTScanner` в
  `core/loader.py` сравнивал имена узлов буквально: `os.system(...)` ловился, а
  `import os as p; p.system(...)` — уже нет. Добавлено отслеживание алиасов
  (`_ALIAS_TRACKED_MODULES`: `os`, `sys`, `shutil`, `importlib`): сканер ведёт
  таблицу `alias → модуль` по `import x as y`, а также по присваиваниям
  `m = __import__("os")` и `m = importlib.import_module("os")` (новые
  `visit_Assign` / `visit_AnnAssign` + `_bind_import_alias`), после чего
  `_resolve_module()` разворачивает алиас во всех проверках вызовов и
  обращений к атрибутам. Дополнительно закрыты: `from os import system`
  (и остальные `_DANGEROUS_OS_ATTRS` в `visit_ImportFrom`), `os.__dict__[...]`
  как способ достать заблокированный атрибут строкой, `getattr(os, 'sys' +
  'tem')` — getattr с вычисляемым, а не литеральным именем атрибута на
  отслеживаемом модуле, и деструктивные вызовы `shutil.rmtree` / `os.remove` /
  `os.unlink` (`_DESTRUCTIVE_ATTRS`), в том числе через алиас и через
  `from shutil import rmtree`. Ложных срабатываний на обычном коде нет:
  переменная с именем вида `os_name` и `shutil.copy()` проходят как прежде.
  Важная оговорка: это фильтр от очевидно вредоносного кода, а НЕ песочница.
  Статический анализ не покрывает случаи, где имя вычисляется только в рантайме
  из недоступных сканеру данных, а также C-расширения и свои загрузчики, поэтому
  проверка чужих модулей глазами перед установкой остаётся обязательной. При
  этом покрытие заметно шире, чем «только буквальные обращения»: закрыты доступ
  к реестру модулей `sys.modules[...]` / `.get()` / `.pop()` / `.setdefault()` со
  статически известным ключом (включая склейку литералов вида `"o" + "s"` и
  алиасы `import sys as s`, `reg = sys.modules`), `import_module` без префикса
  (`from importlib import import_module`, в том числе под алиасом) и `__import__`,
  привязанный к переменной (`f = __import__; f("os")`), косвенный доступ к
  атрибутам через `operator.attrgetter` / `operator.methodcaller` (по имени
  модуля, его алиасу, `from operator import attrgetter [as ...]` и присваиванию
  `ag = operator.attrgetter`) и wildcard-импорты из чувствительных модулей
  (`from os import *`, `from asyncio import *`, `from shutil import *` и т. д.).
  Легитимные идиомы не задеты: `sys.modules[module_name]` с переменным
  нечувствительным ключом, `import_module("json")`, `operator.attrgetter("name")`
  и `from typing import *` проходят как прежде.
- **Сканер закрыл спавн процессов через `asyncio`.** Проверки покрывали
  `os`/`shutil`/`subprocess`, но мимо них проходил запуск внешних процессов
  средствами `asyncio` — модуль мог поднять произвольный процесс, не тронув ни
  одного отслеживаемого имени. Добавлен список `_ASYNC_SUBPROCESS_ATTRS`
  (`create_subprocess_shell`, `create_subprocess_exec`, `subprocess_shell`,
  `subprocess_exec`), и теперь блокируются все синтаксические формы обращения к
  ним: прямой вызов `asyncio.create_subprocess_shell(...)`, вызов через алиас
  модуля и через цепочку импорта, вызов у объекта цикла событий
  (`loop.subprocess_exec(...)`), `from asyncio import create_subprocess_shell`
  (`visit_ImportFrom`) и `getattr(asyncio, "create_subprocess_shell")` с
  литеральным именем атрибута (`visit_Call`). Проверка идёт по точному
  совпадению имени, поэтому свои функции-обёртки вроде
  `create_subprocess_shell_wrapper()` и обычные импорты `from asyncio import
  gather, sleep` продолжают работать.
- **Предупреждение на подозрительный `open()`.** Если модуль открывает путь,
  содержащий `session`, `.key` или `config.toml` (в том числе собранный
  f-строкой со статической частью), сканер пишет в лог
  `AST scan: <файл>: Suspicious open() of path containing ...`. Это именно
  предупреждение в `scanner.warnings`, загрузка не блокируется: у легитимных
  модулей бывают свои `.key`-файлы, а вот попытка прочитать файл сессии теперь
  видна в логе.
- **`crypto.py` берёт путь к `config.toml` из `paths.effective_config_path()`.**
  Раньше `_derive_key_from_credentials()` вне Docker/мультиаккаунта строил путь
  как `Path(__file__).parent.parent / "config.toml"`. Если конфиг лежал в другом
  месте (`KITSUNE_CONFIG`) и при этом не были заданы `KITSUNE_DATA_DIR`/`DOCKER`,
  файл не находился, детерминированный ключ из `api_id`/`api_hash` не выводился —
  и `_load_or_create_key()` молча генерировал случайный ключ. Следствие: после
  перезапуска или переустановки старые зашифрованные бэкапы переставали
  открываться. Теперь путь единый для всего проекта; фолбэк на
  `~/Kitsune/config.toml` сохранён.

### 🐞 Потеря данных: пропущенные `await`

- **`Module.set()` молча терял данные по всему проекту.** В
  `core/loader.py` метод `def set(self, key, value)` вызывал
  `self.db.set(...)` без `await` — корутина никогда не исполнялась. Это
  публичный API, которым пользуются все модули, в том числе сторонние. Теперь
  запись выполняется синхронно через `db.set_sync` / `force_set`, а метод
  возвращает объект `_SyncSetResult`, который одновременно является awaitable.
  Оба стиля вызова — `self.set(...)` и `await self.set(...)` — работают и
  реально пишут в БД; обратная совместимость сохранена полностью.
- **`Pointer.remove()` бросал `AttributeError`.** В `kitsune/pointers.py`
  вызывался несуществующий `self._db.remove(...)` — в `DatabaseManager` есть
  только `delete()`. Теперь используется `delete()` с фолбэком на `remove()`
  для сторонних бэкендов; `ListPointer.remove(item)` не задет переопределением.
- **Остальные пропущенные `await` расставлены:** сохранение конфига модуля и
  настроек ядра в `web/routes_system.py`, `declined_joins` в
  `core/loader.py`, `owner_id` в `modules/notifier/bot_runner.py`.
- **Защита от рецидива.** Добавлен `tools/check_missing_await.py` — AST-скрипт,
  падающий, если вызов async-метода БД (`set`/`delete`/`remove`/`force_save`)
  остался без `await` вне разрешённого списка. Запускается отдельным job в CI.

### 🛠 Надёжность и корректность

- **`assert` убран из потока управления.** В `core/reliability.py` при запуске
  под `python -O` assert выкидывался и получался `raise None` → `TypeError`.
  Заменено на явную проверку с осмысленным `RuntimeError`. Весь `kitsune/`
  прочёсан на аналогичные случаи (в тестах assert'ы оставлены).
- **`isinstance` с локально созданным классом.** В `mtproto_replay.py`
  `_build_hardened_state()` создавал новый тип при каждом вызове, поэтому
  `isinstance(state, Hardened)` всегда был False и идемпотентность
  `ensure_replay_protection()` нарушалась. Фабрика обёрнута в
  `functools.lru_cache(maxsize=1)`; добавлен тест на двойной вызов.
- **Молчаливая подмена edit → send.** В `core/hydro_bridge.py` любой сбой
  `edit_message`, включая сетевой, приводил к отправке нового сообщения —
  в чате плодились дубликаты. Теперь перехватываются только осмысленные ошибки
  (`MessageNotModified`, `MessageIdInvalid`, `MessageAuthorRequired`,
  `MessageEditTimeExpired`), сетевые и флуд-ошибки пробрасываются наверх,
  `FloodWait` уважается, причина fallback пишется в лог.
- **Медиа больше не грузится целиком в RAM.** В `core/hydro_bridge.py` и
  `hydro_media.py` добавлен потоковый режим: при передаче пути или файлового
  объекта данные пишутся на диск без буферизации, а выше порога 50 МБ
  автоматически используется временный файл вместо `BytesIO`.
- **Перезапуск процесса стал корректным.** Раньше `os.execl` вызывался в 6
  местах без завершения работы — терялись несохранённые данные. Добавлена единая
  `kitsune/_internal.py::graceful_restart()`, которая выполняет
  `await db.force_save()`, отключает Telethon и Hydrogram, останавливает
  веб-сервер, отменяет фоновые задачи и завершает процессы твинков, переиспользуя
  готовый shutdown из `core/lifecycle.py`. Ею заменены все вызовы в
  `modules/updater.py` и `modules/notifier/update_checker.py`.
- **Дублирующийся вызов и мёртвый код удалены:** повторный
  `await self.db.set(_DB_OWNER, "pending_update", {...})` в `modules/updater.py`
  и ветка `if False and arg == "1m"` в модуле бэкапов. Проект прочёсан на
  аналогичные заглушенные ветки.
- **`_start_time` в `modules/ping.py`** перенесён из атрибута класса в
  `__init__` — реального бага не было (значение приоритетно читается из БД), но
  ловушка на будущее устранена.
- **`low_power = true` из `config.toml` доводит режим до конца.**
  `utils/platform.py::is_mobile()` учитывал только переменную окружения
  `KITSUNE_LOW_POWER`, а ключ из конфига — нет. В итоге режим экономии работал
  наполовину: задержка автосохранения БД и политика ретраев подключения
  подхватывали `low_power` из `config.toml`, а мобильная ветка PRAGMA для
  SQLite — нет, и на слабом устройстве база продолжала работать в
  «десктопных» настройках. Теперь `is_mobile()` спрашивает
  `low_power.resolve(load_config())`, конфиг и переменная окружения дают
  одинаковый результат (переменная по-прежнему приоритетнее).
- **Восстановление БД сессии больше не молчит.** В `session_enc.py`
  `except Exception: pass` внутри цикла `iterdump()` создавал частично
  восстановленную битую базу. Теперь ошибки считаются, первые из них
  логируются, а при превышении порога доли ошибок восстановление **прерывается**:
  оригинал сохраняется как `.session.corrupt.<ts>`, пользователь получает
  внятное сообщение о необходимости повторного входа.
- **Отсутствие опциональных зависимостей `aiogram` и `toml` больше не молчит.**
  Обе библиотеки импортируются в `try/except ImportError`, и при их отсутствии
  функциональность отключалась совершенно бесшумно: `generate_markup()` в
  `inline/core/markup.py` возвращал `None`, из-за чего у форм, галерей и списков
  просто не появлялись кнопки, а `low_power.load_config()` возвращал `{}`, то
  есть `low_power = true` из `config.toml` тихо игнорировался и слабое
  устройство продолжало работать в «десктопных» настройках. В логе при этом не
  было ни строки — пользователь видел только «кнопки не работают» без причины.
  Теперь каждая точка мягкой деградации **один раз** пишет `logger.warning()` с
  явным названием отсутствующего модуля и подсказкой по установке
  (`pip install aiogram` / `pip install toml`). Для aiogram добавлен хелпер
  `inline/core/common.py::warn_no_aiogram_once(feature, disabled)` с реестром
  уже предупреждённых точек — предупреждение выдаётся для каждой из них
  отдельно, но не повторяется при последующих вызовах, так что лог не засоряется
  на каждый рендер клавиатуры. Он покрывает три соседних молчаливых пути:
  `generate_markup()` (клавиатуры отключены), `InlineManager.start()`
  (inline-бот не поднимается, недоступны формы/галереи/списки и обработчики
  личных сообщений бота) и `dispatch.edit()` (редактирование inline-сообщений
  становится no-op). В `low_power.py` появились `_warn_no_toml_once()` и
  `_warn_config_unreadable_once(reason)`: первый сообщает именно об отсутствии
  `toml`, второй — о недоступном `config.toml`, причём отдельно по каждой
  причине (не удалось получить путь, `stat()` не прошёл, файл не парсится), так
  что «нет библиотеки» и «нет/битый файл» больше не путаются между собой.
  Поведение самого юзербота не изменилось: деградация остаётся мягкой, никаких
  новых исключений не бросается, `generate_markup()` по-прежнему возвращает
  `None`, `load_config()` — `{}` (или прежний кэш), а `KITSUNE_LOW_POWER`
  продолжает работать без `toml`. Для тестов у обоих реестров есть
  `reset_optional_dep_warnings()`. Покрыто в
  `tests/test_optional_dep_warnings.py`: проверяется, что предупреждение
  появляется, что оно ровно одно при повторных вызовах, что при установленных
  `aiogram`/`toml` лишнего шума в логе нет и что каждая точка деградации
  предупреждает отдельно.

- `tools/healthcheck.py` — healthcheck для Docker: опрашивает `/health`,
  порт берёт из `config.toml` (`web_port`) с фолбэком на `KITSUNE_WEB_PORT`.
- **SQLite-база переехала в каталог данных.** `DatabaseManager.init()` создавал
  `kitsune-<tg_id>.db` рядом с исходниками; в Docker это слой контейнера, и при
  каждой пересборке образа вся база — настройки модулей, алиасы, указатели —
  исчезала вместе со слоем. Теперь путь строится от `paths.data_dir()`, то есть
  ложится на том `/data` (или в `~/.kitsune` вне контейнера). Для уже
  работающих установок добавлена однократная автомиграция
  `_migrate_legacy_db()`: старый файл переносится на новое место вместе с
  `-wal`, `-shm` и `-journal`, перенос выполняется только если старый файл
  есть, а нового ещё нет, сбой переноса не роняет запуск и пишется в лог.
- **Единый источник пути к `config.toml` — `paths.effective_config_path()`.**
  Путь к конфигу самостоятельно строили от `__file__` пять разных мест:
  `modules/settings.py`, `modules/notifier/bot_setup.py`,
  `database/manager.py`, `low_power.py` и `crypto.py`. В Docker и в
  мультиаккаунт-сценариях эти пути расходились с реальным `CONFIG_PATH`, из-за
  чего изменение префикса через `.prefix` или сохранение токена бота-нотификатора
  писалось в файл, который при следующем старте никто не читает — правки тихо
  терялись при рестарте. `effective_config_path()` отдаёт `main.CONFIG_PATH`
  (там уже учтены `KITSUNE_CONFIG`, Docker и вторичный аккаунт), а при
  недоступности `main` — `paths.config_path()`; все пять мест переведены на неё.
- **Liveness и readiness разделены в `tools/healthcheck.py`.** Эндпоинт
  `/health` отдаёт агрегат `ok = sqlite AND redis AND telegram`, а Docker
  трактовал любой не-200 как «контейнер мёртв». Обрыв Telegram (FLOOD_WAIT,
  потеря сети, открытый circuit breaker) даёт 503 при полностью живом процессе —
  контейнер уходил в рестарт-луп и переподключиться уже не успевал. Новая
  `_tolerable_degradation()` разбирает тело ответа: если процесс отвечает и
  SQLite жива (или вовсе не активна — например, при Redis в качестве основного
  бэкенда), деградация считается readiness-проблемой и healthcheck возвращает 0.
  Мёртвая SQLite и неразбираемое тело ответа по-прежнему означают рестарт.

### ⚡ Производительность на Termux и UserLand

- **Раздельная стратегия SQLite для Termux и UserLand.** Обе платформы
  считались одинаково «мобильными» и получали ветку `journal_mode=DELETE`,
  `mmap_size=0`. Для UserLand это оказалось худшим вариантом: там процесс
  выполняется под proot (ptrace), и DELETE пересоздаёт журнальный файл на каждом
  коммите, а каждый файловый syscall стоит дорого. Замер `strace` на 300
  коммитах: `WAL + mmap=0` — 3482 syscall / 85 мс, `DELETE + mmap=0` — 10536 /
  295 мс, то есть разница около 3×. Добавлен детектор
  `utils/platform.py::_detect_proot()` (ненулевой `TracerPid` в
  `/proc/self/status`, плюс UserLand-каталоги при не-Android ядре), а
  `database/manager.py::_journal_settings()` теперь разводит три случая: под
  proot — WAL с `mmap_size=0` и `wal_autocheckpoint=10000`, на Android/Termux —
  DELETE с `mmap_size=0`, на десктопе — WAL с `mmap_size=64 МБ`.
- **`install.sh` и `termux.sh` доведены до мобильных реалий.** Добавлена
  установка `uvloop` (сначала с системным `libuv` через `pkg`/`apt`, при
  неудаче — вендорный, при полном провале работа продолжается на стандартном
  asyncio с предупреждением), прекомпиляция байткода `compileall -q -j 0` для
  `kitsune/` и для зависимостей (первый запуск на слабом устройстве больше не
  тратит минуты на компиляцию `.pyc`), и авто-включение `low_power = true` в
  `config.toml` при установке в Termux/UserLand — если ключ уже задан вручную,
  скрипт его не трогает.

### 🌙 Логи бота прямо из чата — команда `.logs`

- **Новый встроенный модуль `kitsune/modules/logs.py` (команда `.logs`,
  доступ `OWNER`).** Было: чтобы посмотреть, что произошло внутри бота, надо
  было идти на хост и читать файл лога руками — из Telegram логи были
  недоступны. Стало: `.logs` без аргументов показывает inline-клавиатуру с
  выбором уровня (☢️ Critical / 🚫 Error / ⚠️ Warning / ℹ️ Info / 🐞 Debug /
  🧑‍💻 All, по две кнопки в ряд плюс «Отмена»), а `.logs 30` / `.logs warning`
  сразу собирает выборку нужного уровня. Записи берутся из уже работающего
  `KitsuneLogsHandler` (`dumps(level, client_id=...)`), поэтому в файл попадают
  только строки текущего аккаунта. Результат уходит документом
  `kitsune-logs.txt` с caption, где указан уровень, версия сборки и ссылка на
  текущий коммит. Почему: диагностика по просьбе «покажи, что у тебя в логах»
  теперь занимает одно сообщение вместо SSH-сессии.
- **Защита от случайной публикации личных данных.** Уровни ниже `WARNING`
  (`INFO`, `DEBUG`, `All`) содержат отладочные детали, поэтому запрос такого
  уровня сначала открывает экран-предупреждение с кнопками «📤 Всё равно
  отправить» / «🚫 Отмена»; без inline-бота работает текстовый путь с явным
  флагом (`.logs 10 force`). Перед отправкой текст проходит цензуру: из него
  вырезаются номер телефона аккаунта, токен inline-бота
  (`kitsune.notifier` → `bot_token`) и строка сессии Telethon. Если логов
  запрошенного уровня нет — приходит короткое сообщение, а не пустой файл.
  Почему: удобная выгрузка логов не должна превращаться в утечку
  учётных данных.

### 🧩 Новые плейсхолдеры в `.info` и `.ping`

- **`{os}`** — дистрибутив из `PRETTY_NAME` в `/etc/os-release`, с откатом на
  `platform.system()`.
- **`{kernel}`** — версия ядра (`platform.release()`).
- **`{hostname}`**, **`{user}`** — имя хоста и текущий пользователь.
- **`{cpu}`** — модель процессора и ядра в формате
  `Intel(R) Core(TM) i5-9400F; 6 (6) core(-s)`: модель берётся из `/proc/cpuinfo`
  (строка `model name`), при её отсутствии — `platform.processor()`. Загрузка CPU
  осталась отдельным плейсхолдером **`{cpu_usage}`** и не менялась.
- **`{env}`** — среда запуска отдельно от `{platform}`: Termux, UserLand, Docker,
  WSL (с именем дистрибутива) или bare-metal.
- **`{ping}`** — реальная задержка ответа Telegram в миллисекундах. Замеряется
  именно сетевой вызов `client.get_me()` внутри `.info` (а не весь
  `asyncio.gather`), результат кэшируется в `_last_ping_ms`.
- Все геттеры отказоустойчивы: любая ошибка превращается в `—`, сообщение не
  ломается. В `.ping` доступен тот же набор, кроме `{ping}` (там уже есть `{ms}`).

### 📊 Честные метрики веб-панели

- **CPU.** Раньше `/api/status` звал `psutil.cpu_percent(interval=0.2)` без

### 🧭 Обновление до 1.4.4 — что проверить вручную

Апдейт автоматический, но четыре вещи стоит проверить руками.

- **Токен веб-панели.** После первого запуска новой версии Kitsune пришлёт в
  «Избранное» сообщение с токеном и готовой ссылкой
  `http://127.0.0.1:8080/?token=...`. Открой её один раз — токен ляжет в
  httpOnly-cookie, дальше панель работает как прежде; тот же токен дублируется в
  лог при старте. Для скриптов — заголовок `Authorization: Bearer <токен>`.
  Старые закладки на `localhost:8080` без токена теперь дают `401`.
- **Панель слушает `127.0.0.1`.** Если раньше ты заходил с другого устройства —
  пользуйся SSH-туннелем (`ssh -L 8080:127.0.0.1:8080 user@сервер`) либо осознанно
  открой `web_host = "0.0.0.0"` в `config.toml` (только за reverse-proxy с HTTPS).
- **Бэкапы: новый вывод ключа и файл соли.** Старые архивы расшифровываются как
  раньше (сначала новый ключ PBKDF2, при неудаче — legacy). Рядом с ключом
  появляется файл соли с правами `0600` — не удаляй его и клади в личный бэкап
  вместе с ключом, иначе новые архивы не откроются после переустановки. Первый
  бэкап после апдейта создаётся уже в новом формате.
- **Docker: подключи том.** Убедись, что у контейнера смонтирован том в `/data` и
  что там лежат `config.toml`, `*.session` и БД (`docker compose exec kitsune
  ls -la /data`). Если старая сессия осталась внутри контейнера — скопируй её до
  пересоздания: `docker cp kitsune:/root/.kitsune/. ./kitsune-data-backup/`,
  иначе просто пройди авторизацию заново.

### 🔁 Импорт/экспорт алиасов и переключение команд

#### ✨ Новое

- **Импорт алиасов из файла — `.loadaliases` (`.la`).** Принимает `.json`-файл
  (реплаем или прикреплённый к команде) формата
  `[{"alias": "длм", "command": "dlm"}, ...]`. Дубликаты и неизвестные команды
  пропускаются, остальные добавляются и сохраняются в БД. Разбор и валидация
  выполняются до записи, файл скачивается через `event`-API Kitsune (так же,
  как в `loader_mod`).
- **Экспорт алиасов — `.aliasload` (`.al`).** Выгружает все текущие алиасы
  обратно в `kitsune_aliases.json` — удобно для переезда конфигов между
  инстансами.
- **Переключение команд — `.togglecmd`.** `togglecmd <команда>` или
  `togglecmd <модуль> <команда>` — отключает/включает конкретную команду модуля
  (проверяется принадлежность команды модулю). Отключённая команда молча
  игнорируется диспетчером, в т.ч. при вызове через алиас и на входящих командах.
- **`.disabledcmds`** — список отключённых команд.
- **Слой отключения в `core/dispatcher.py`:** `disable_command`,
  `enable_command`, `is_command_disabled`, `get_disabled_commands`,
  `load_disabled_commands`. Проверка встроена в `_handle_message` и
  `_on_in_message` до проверки прав — без физической выгрузки, поэтому переживает
  перезагрузку модуля (флаг хранится в диспетчере, а не в объекте модуля).
- **Персистентность** в БД (`kitsune.core` → `disabled_commands`), восстановление
  в `core/lifecycle.py` после загрузки модулей.

#### 🧪 Тесты

- `tests/test_aliases.py` расширен: enable/disable, roundtrip загрузки,
  блокировка цели алиаса по флагу.

### 🏷 Пользовательские алиасы команд

#### ✨ Новое

- **Рантайм-алиасы команд.** Любую команду теперь можно вызвать под своим
  псевдонимом, в том числе на кириллице: `.addalias длм dlm` → команда `.длм`
  работает как `.dlm`. Механика реализована в архитектуре диспетчера Kitsune:
  подстановка выполняется при разборе команды, сигнатуры целевых обработчиков
  не дублируются.
- **Слой алиасов в `core/dispatcher.py`.** Добавлены `add_alias`,
  `remove_alias`, `resolve_alias`, `get_aliases`, `load_aliases`. Разрешение
  алиаса происходит только если целевая команда зарегистрирована; алиас не может
  перекрыть настоящую команду. При выгрузке команды её алиасы автоматически
  снимаются (`unregister_command`).
- **Baked-in аргументы.** Алиас может нести часть аргументов:

  присваивание `raw_text`.
- **Команды в `modules/settings.py` (v1.4.0):** `.aliases` (список),

  `.delalias` (по одному/списком, `-c`/`--clear` для полной очистки). Все строки
  в стиле Kitsune (RU), с HTML-escape и раскрывающимися blockquote.
- **Персистентность.** Алиасы хранятся в БД (`kitsune.core` → `aliases`) и
  восстанавливаются в `core/lifecycle.py` после загрузки всех модулей.
- **Интеграция в `.help`.** В карточке модуля рядом с командой показываются её
  пользовательские алиасы.

## [1.4.3] — Фиксы автоустановки зависимостей и выгрузки модулей

### 🐞 Загрузка/установка зависимостей
- **Исправлен маппинг пакета для нового Google SDK.** В `kitsune/core/loader.py`
  словарь `_IMPORT_TO_PIP` теперь связывает импорт `google` с актуальным
  пакетом **`google-genai`** (было устаревшее `google-generativeai`).
  Модули, использующие `from google import genai` (например пользовательский
  `GeminiK`), теперь корректно доустанавливают зависимость при первой загрузке.
- `google-genai` добавлен в набор namespace-пакетов (`_NAMESPACE_PKGS`)
  в `_pip_install`; старый `google-generativeai` там сохранён ради
  обратной совместимости.
- **`.sh` / терминал теперь ставит пакеты в venv бота.** В
  `kitsune/modules/terminal.py` добавлена функция `_venv_aware_env()`:
  каталог текущего интерпретатора (`sys.executable`) ставится первым в `PATH`,
  а при настоящем venv (наличие `pyvenv.cfg`) выставляется `VIRTUAL_ENV`
  и убирается `PYTHONHOME`. Раньше `.sh pip install ...` мог попадать
  в системный/`--user` Python мимо venv.

### 🐞 Выгрузка модулей (`.unloadmod` / `.ulm`)
- **Модуль больше не «живёт» после выгрузки.** В `unload_module`
  (`kitsune/core/loader.py`) добавлена очистка `sys.modules`
  (метод `_purge_sys_modules`): удаляются и сам Python-модуль, и все его
  подмодули, после чего вызывается `importlib.invalidate_caches()`.
  Это устраняло причину, по которой фоновые asyncio-задачи, замыкания
  и напрямую навешенные telethon-хендлеры продолжали работать
  до полной перезагрузки процесса.
- **Снятие inline-хендлеров при выгрузке.** Добавлен
  `_unregister_inline_handlers_for`; в `inline/core.py`
  `unregister_inline_handler` теперь сопоставляет связанные методы
  по `__self__`/`__func__`, а не по `is` (иначе rebound-метод из
  `inspect.getmembers` не находился). Callback-хендлеры в текущей версии
  не задействованы (декоратора и регистрации нет), поэтому мёртвый код
  не добавлялся.
- **Watcher'ы и команды снимаются по модулю-владельцу.** В диспетчере
  (`kitsune/core/dispatcher.py`) `register_watcher` сохраняет владельца
  явным полем, а `unregister_watchers_for` снимает по нему — теперь
  корректно снимаются и watcher'ы, зарегистрированные как несвязанные
  функции/замыкания (без `__self__`). Проверка по `__self__` оставлена
  как дополнительный критерий. Команды снимаются по модулю из записи
  диспетчера, а не только по `__self__`.

### 🔬 Tests
- Новый файл `tests/test_unload_fixes.py`: маппинг `google → google-genai`,
  снятие watcher'а по владельцу (в т.ч. для функции без `__self__`),

## [1.3.0] — Phase 3: Reliability

### 🛡 Reliability subsystem
- **Новый модуль `kitsune/core/reliability.py`** с полным набором инструментов надёжности:
  - `CircuitBreaker` — классический «автоматический выключатель»
    с тремя состояниями (CLOSED → OPEN → HALF_OPEN), async-safe.
  - `RetryPolicy` + `retry_with_backoff()` — экспоненциальный backoff
    с jitter для сетевых операций (1с → 2с → 4с → 8с → 16с).
  - `DegradationFlags` — глобальные флаги graceful degradation
    (`hydrogram_failed`, `assets_unavailable`, `redis_unavailable`, `vpn_down`).
  - `global_registry` — единый реестр всех breaker'ов.

### 💗 Health endpoint & модуль
- **Команда `.health`** переписана полностью (`kitsune/modules/health.py`):
  - Параллельные пробы SQLite (`SELECT 1`), Redis (`PING`),
    Telegram session (`GetStateRequest` под защитой breaker'а).
  - Latency-измерения для каждой подсистемы.
  - Статус всех circuit breaker'ов + флаги деградации.
  - Uptime, RAM/CPU/disk, process RSS.
- **Новые команды**: `.breakers`, `.resetbreaker <name>`.
- **HTTP `/health`** в web/core.py возвращает тот же расширенный JSON-snapshot;
  при проблемах отвечает HTTP 503 (удобно для load-balancer'ов).

### ⚡ Circuit breakers в боевых местах
- **`telegram_api`** (5 fail / 60с cooldown) — защищает GetState-probe.
- **`redis_io`** (3 fail / 30с cooldown) — после 3 провалов
  `DatabaseManager` автоматически фоллбекится на SQLite,
  без потерь данных.
- **`hydrogram_io`** (3 fail / 5 мин cooldown).

### 🔄 Graceful degradation
- **Hydrogram сломался → Telethon-only**: `hydro_media.py` после
  3 провалов подряд помечает Hydrogram мёртвым на 5 мин и всё
  время идёт напрямую через Telethon. PEER_ID_INVALID не считается
  системным сбоем. `HydrogramBridge` респектит флаг.
- **Assets channel недоступен → пропускаем медиа**:
  `store_asset()`/`fetch_asset()` больше не бросают RuntimeError,
  возвращают None и пишут в debug-лог.
- **Redis отвалился → SQLite-fallback**: `DatabaseManager` держит
  «тёплый» SQLite-backend наготове; переключение мгновенное,
  порог — 3 провальных save подряд.
- **VPN/прокси отключился → retry с backoff**: `_safe_force_reconnect()`
  в main.py использует `retry_with_backoff` и поднимает флаг
  `vpn_down` на время retry-цикла.

### ✋🏻 Tests
- `kitsune/tests/test_reliability.py` — 18 unit-тестов:
  CircuitBreaker (states/transitions/reset), RetryWithBackoff (success/
  retry/exhaust), DegradationFlags, registry. Все проходят (`OK`).

### 🔧 Misc
- Redis-клиент теперь создаётся с `socket_timeout=5s`,
  `socket_keepalive=True`, `health_check_interval=30s` — хвист ловит
  обрывы быстрее.

  при каждом старте. Если DB всё равно readonly — пересоздаётся через dump/restore.
- **Hydrogram запрашивает номер телефона в консоли** — Hydrogram больше не стартует

- **FilePartEmptyError при бэкапе** — позиция BytesIO буфера сохраняется перед попыткой
  отправки через Hydrogram и сбрасывается при fallback на Telethon.

  для кэширования entity в Hydrogram.
